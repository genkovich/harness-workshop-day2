# Ранбуки · день 2

Учора ми самі написали харнес: цикл, історію повідомлень, виконання тулів, повтор після 429, skills і guard. Сьогодні той самий агент живе в Telegram, а харнес бере на себе [Flue](https://flueframework.com/docs/guide/why-flue/). Наше завдання на практиці: зрозуміти, що саме він забрав, і що лишилося нам.

Почни з [підготовки](00-setup.md). Репозиторій клонуємо разом на початку заняття. Під час практики змінюємо лише `src/`.

## Що будуємо

Особистий бот для нотаток. Пишеш йому «запамʼятай: у пʼятницю реліз», потім питаєш «що в мене з релізом?» або «зроби стендап». Власник бота може ще й видалити свої нотатки, інші користувачі такої можливості не мають.

## Учора писали самі, сьогодні робить Flue

| Учора, свій харнес | Сьогодні, Flue | Де це видно в коді |
|---|---|---|
| `for`-цикл у `runAgent`, зупинка, коли модель не просить тул, ліміт кроків | Цикл веде runtime | Ніде: цього коду в нас більше немає |
| `messages[]` жив лише один запуск `npm start` | Історія розмови зберігається за id агента в SQLite | `init(Assistant, { id })`, файл `bot.db` |
| Опис у `tool()`, схема Zod і `switch` у `runTool` окремо | Один обʼєкт `defineTool`: назва, опис, схема, `run` | `src/tools.ts` |
| `schema.parse`, `try/catch` в `executeTool`, помилка як `{ error }` | Flue перевіряє аргументи й повертає помилку моделі як результат тула | Ніде |
| `addToolResult` з тим самим `toolCallId` | Runtime сам кладе результат в історію | Ніде |
| Повтор після 429 і `Retry-After` (етап 08б) | Runtime повторює хід моделі з обмеженим бюджетом спроб | Ніде |
| Другий запит під час першого зіпсував би спільний `messages[]` | Runtime впорядковує повідомлення одного id, історія не ламається | Ніде |
| Каталог описів і тул `readSkill` | `useSkill`: каталог у system prompt і тул `activate_skill` | `src/skill.ts` |
| `beforeTool` блокує виклик перед виконанням | Тула, який не дозволено, просто немає в списку | `if (isOwner(id)) useTool(...)` |
| `console.log` на кожному кроці циклу, `TRACE=1` | `flue run` друкує кроки сам; для бота є хук `useResponseFinish` | `src/log.ts` |

## Що лишилося нам

Flue не знає, що агент уміє, чиї це дані, кому що дозволено і куди приходять повідомлення. Це і є наш код:

| Файл | Відповідає за | Етап |
|---|---|---|
| `src/notes.ts` | Нотатки у `notes.json`. Звичайний код застосунку, про модель нічого не знає | готовий у `start` |
| `src/models.ts` | Модель першого дня: додає Qwen 3.8 у каталог Groq, бо Flue 2.0.6 її ще не знає | готовий у `start` |
| `src/agent.ts` | Агент: модель, інструкція, які тули й skills йому доступні | 01, далі росте |
| `src/chat.ts` | Місток: повідомлення чату → агент з id цього чату → текст відповіді | 02 |
| `src/bot.ts` | Telegram: отримати повідомлення і надіслати відповідь | 02 |
| `src/tools.ts` | Тули над `notes.ts`. `chatId` підставляє код, модель його не бачить | 03 |
| `src/settings.ts` | Хто власник бота. Читає код, модель цього не бачить | 04 |
| `src/log.ts` | Рядок журналу після кожної відповіді: які тули, скільки токенів | 05 |
| `src/skill.ts` | Skill `standup` з `skills/standup/SKILL.md` | 06 |

**Дві різні памʼяті.** Історію розмови веде Flue: вона лежить у SQLite і привʼязана до id агента. Нотатки веде наш застосунок: вони лежать у `notes.json`, і Flue про них нічого не знає. Історія допомагає моделі памʼятати контекст розмови, нотатки лишаються даними, які можна відкрити, перевірити й видалити. У Flue є і свій механізм стану (`usePersistentState`), але нам потрібен файл, який бачить людина. Учора ми так само перевіряли вміст `.data/digest.md`: слова моделі нічого не доводили.

**Два сховища історії.** `npm run ask` пише історію в `node_modules/.cache/flue/run.db`, бот пише в `bot.db`. Тому розмова в терміналі й розмова в Telegram не бачать одна одну, навіть з однаковим id. Щоб почати розмову заново, видали відповідний файл: для терміналу `node_modules/.cache/flue/run.db`, для бота `bot.db` (бота спершу зупини).

## Тести

Тести ганяють справжній цикл Flue, але замість моделі підставляють скрипт ([tests/model.ts](../tests/model.ts)). Скрипт каже, що «відповідає модель»: текст або виклик тула. Тест бачить усе, що модель отримала: інструкцію, історію, список тулів. Так ми перевіряємо без мережі й без ключа, що `saveNote` справді записує файл, а чужий чат справді не бачить `deleteNotes`.

Номер на початку назви тесту = етап. Команда в кожному ранбуку запускає цей і попередні етапи:

```bash
npm test -- --test-name-pattern "^(00|01|02) "
```

На `main` і `step-06-skill` запускай просто `npm test`. Тести не доводять, що жива модель поведеться так само: це перевіряємо руками через `npm run ask` і бота.
